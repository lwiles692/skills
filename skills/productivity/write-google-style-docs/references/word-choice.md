# Word choice and terminology

## Decide which term wins

Use this order:

1. Preserve exact UI labels, identifiers, protocol terms, and official product names.
2. Follow the project's established glossary or terminology decisions.
3. Check the current Google developer documentation word list for a term-specific rule.
4. Use the first Merriam-Webster spelling for unresolved general English spelling.
5. Prefer the clearest established term for the target audience and use it consistently.

Treat a Google word-list label as follows:

- **Use with caution:** Prefer a clearer term, or define the necessary term on first use.
- **Don't use:** Replace the term in prose. If it appears in code or an external interface, preserve the literal text in code font and write around it.
- Product badge or annotation: Apply the rule only to that product's documentation.

## Abbreviations

- Use an abbreviation only when it saves readers time.
- Spell out an unfamiliar term on first use and put the abbreviation in parentheses. Use the abbreviation alone afterward.
- Don't add an abbreviation that appears only once unless readers know the abbreviation better than the long form.
- Don't automatically expand common developer terms such as **AI**, **API**, **HTML**, **PDF**, **RAM**, **REST**, **URL**, and **XML**.
- Don't create an abbreviation to shorten prose.
- Avoid **e.g.** and **i.e.**; use **for example** and **that is**.
- Avoid **etc.**, internet slang, and abbreviations used as verbs.
- Form plurals without an apostrophe: **APIs**, not **API's**.

## Common high-impact choices

Prefer these patterns unless a literal interface or domain term requires otherwise:

| Avoid or use carefully | Prefer |
| --- | --- |
| allows you to | lets you |
| click here | descriptive link text |
| could, would | can, might, or a direct statement |
| desire, desired | want, need, or the specific requirement |
| dummy variable | placeholder, indicator variable, or the precise statistical term |
| leverage, utilize | use |
| please note | state the information directly |
| sanity check | final check, confidence check, or validation |
| simple, simply, easy, easily, quick, quickly | omit the judgment or state a measurable fact |
| traditional | conventional, on-premises, legacy, or another precise term |
| wish | want or need |

Use **sign in** and **sign out** for authentication actions unless an interface or established domain uses another term. Use **setup** as a noun or adjective and **set up** as a verb.

## Jargon and emerging terms

- Write around jargon when a plain term is accurate.
- Retain a search-relevant or industry-standard term only when readers need it. Define it on first use and then use it consistently.
- Don't use casing names such as **camel case** or **snake case** when localization matters. Describe the pattern and provide an example.
- For a disputed, fast-changing, product-specific, or sensitive term, verify the current official word-list entry rather than relying on this summary.
