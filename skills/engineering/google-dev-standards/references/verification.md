# 验证与审查流程

本文件是将四组规范用于实际项目的**工程实践**，不代表 Google 原文额外规定了统一工具链。
先采用仓库现有配置和命令，再考虑下面的候选检查。

## 收集项目约束

先确认工作目录和目标文件，读取用户指定范围内的约定。
仅在存在相应项目时查找下列证据，不要求每个仓库具备所有文件。

| 目标 | 常见证据 |
| --- | --- |
| 贡献约定 | `AGENTS.md`、`CONTRIBUTING.md`、现有代码、CI 检查命令 |
| C++ | 构建系统、编译标准选项、`.clang-format`、`.clang-tidy`、公开 ABI 约束 |
| Go | `go.mod` 的 `go` / `toolchain` 指令、构建标签、现有 import 分组、检查配置 |
| Python | `pyproject.toml`、支持版本、格式化器配置、`.pylintrc`、已采用的类型检查器 |
| Markdown | 文档宿主、构建配置、链接路由、目录支持、Markdown 检查配置 |

记录项目约定与 Google 默认规则的差异，保留合理的迁移边界。
没有明确项目约定时才采用默认值；避免为消除单个差异修改全仓库配置。

## 按风险选择验证

| 改动 | 最小有效验证 |
| --- | --- |
| 纯排版或局部命名，行为不变 | 对改动文件运行既有格式/静态检查并复查 diff；有接口影响时另查调用方 |
| 注释或 Markdown | 核对事实、链接、代码示例与目标平台渲染 |
| 错误分支、解析、状态或接口行为 | 针对相应行为运行或补充有价值的测试 |
| 生命周期、异步取消或共享状态 | 验证退出与清理路径；环境适合时使用项目现有的竞态/内存检查 |
| 构建或类型配置变化 | 验证受影响目标，记录工具版本与配置作用范围 |

不要为低影响的格式更改重复运行无关全量测试。
不要把“命令退出为 0”扩展解释成全部业务正确或完全符合 Google 规范。

## 各语言验证

### C++ 验证

1.  确认构建配置实际使用的标准版本和平台；不自动修改标准选项。
2.  已有 `.clang-format` 时按该配置检查本次文件。
    `clang-format --dry-run --Werror path/to/file.cc` 是支持这些参数的版本的候选命令。
    无配置且用户要求 Google 格式时，可评估 `-style=Google`，并先预览差异。
3.  使用项目已有的编译与测试入口；有配置时运行相关 `clang-tidy` 或其他检查。
    编译器和 formatter 都无法替代对所有权、悬垂引用、接口契约的人工审查。
4.  不根据 Google 的内部实现约束，擅自移除外部工程依赖的异常或引入新库。

### Go 验证

1.  对改动文件运行 `gofmt -d path/to/file.go` 查看差异；用户要求修改时再使用写入模式。
    `goimports` 仅在项目采用时使用，不把它视为所有项目的强制依赖。
2.  对相关包使用 `go vet` 与 `go test`。范围适合时可以使用 `go vet ./...`、
    `go test ./...`；大型仓库、集成环境或额外资源需求应遵循仓库入口。
3.  并发修改可考虑受支持平台上的 `go test -race`，但不要声称竞态检测能证明无竞态。
4.  关注依赖下载、构建标签、工具链与测试环境造成的限制；不为通过验证自动升级版本。

### Python 验证

1.  优先运行项目现有的 formatter 与 `pylint` 配置；formatter 的选择和版本由项目确定。
    可使用 `python -m pylint path/to/module.py` 作为已安装对应工具时的候选入口。
2.  对新增或修改的公开 API 检查类型注解，并运行项目采用的类型检查器。
    没有构建集成时报告缺口，不擅自替换现有检查器或装入新依赖。
3.  按行为改动运行项目测试入口；`pytest`、`unittest` 等依据仓库已有选择。
4.  不能用 `compileall` 或格式化通过，替代资源关闭、异常路径与并发语义验证。

### Markdown 验证

1.  使用现有检查器与文档构建命令，确认规则适用于目标 Markdown 方言。
2.  检查唯一 H1、目录、列表嵌套、代码围栏与语言、链接、图片替代文本。
3.  对代码示例做语法或可执行性核对；标注示例所需版本和外部依赖。
4.  对 `[TOC]`、站点根链接、原生 HTML 等平台相关内容检查实际渲染效果。
5.  断网或无渲染器时明确验证边界，不报告虚构的链接/渲染通过结果。

## 报告结构

按任务选择“实现交付”或“审查发现”，避免输出不必要的完整模板。

### 实现交付

1.  结果：完成了什么，以及对调用者/读者的具体影响。
2.  关键决策：与项目约定、Google 默认规则及兼容性的关系。
3.  验证：实际运行的命令、结果及必要的范围说明。
4.  限制：无法执行的检查、尚未确定的条件和剩余风险。

### 审查发现

按影响排序；一条发现聚焦一个可修复的问题。

```text
位置：src/example.py:42
规则：PY-XX（必须／默认／建议，按实际条款填写）
现象：引用可定位的代码或行为。
影响：说明真实后果，区分行为缺陷和样式偏差。
最小修正：给出可执行的修改建议。
依据：官方章节链接；说明是否存在项目例外。
验证：已运行检查及结果；未执行项说明原因。
```

上述 `PY-XX` 是格式占位符，实际交付必须换为参考文件存在的规则编号。
测试与格式检查采用清楚的状态：通过、失败、未执行、不适用。
失败原因区分代码问题、已有问题与环境限制；不得把未执行记为通过。

## 防止误报

-   先查看上下文：空切片与 `nil`、空字符串与 `None` 等差异可能是接口契约。
-   先核对版本：不要强推项目最低版本不支持的语法或 API。
-   先核对原文强度：不要把 Go Best Practices 或示例偏好标成强制门禁。
-   先核对公开接口：外部协议、框架回调和兼容性可能约束名称与函数签名。
-   不推断所有链式调用、所有长函数或所有缩写都有问题；结合可读性与具体条款。
-   不为“更符合风格”修改可观察行为，例如错误类型、JSON 空值、异常传播与日志语义。
-   遇到正式采用的 formatter 与人工排版偏好冲突时，优先现有配置并记录差异。
