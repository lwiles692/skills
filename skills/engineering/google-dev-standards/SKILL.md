# Google 多语言开发规范

将官方规范应用于具体改动，提供有依据、可验证、范围明确的实现或审查结果。
本技能覆盖 C++、Go、Python 与 Markdown；不要据此推导其他语言的 Google 规则。
来源核验日期：2026-10-28。正文为中文整理，示例为原创；详细出处见
[来源与适用边界](references/sources.md)。

## 先确定适用范围

1.  识别任务是编写、重构、审查、解释规范还是配置工具。
    仅审查时给出发现与修复建议；用户要求修改时直接完成范围内的修改。
2.  读取仓库的 `AGENTS.md`、贡献指南、构建配置、格式化与静态检查配置。
    优先使用 `rg --files` 和 `rg` 查找相关文件，只读取任务所需内容。
3.  确认目标文件、已有 diff、语言版本、公开接口兼容性及 Markdown 渲染平台。
    默认排除第三方代码、生成文件、锁文件和无关文件。
4.  遵循用户明确要求及适用的项目约定；没有约定时采用本技能的 Google 默认规则。
    用户明确要求严格对齐 Google 而现有项目存在冲突时，指出冲突和影响，
    完成无冲突部分；需要破坏兼容性或超出任务范围时再请求决定。
5.  区分“采用 Google 风格”和“复刻 Google 内部环境”。
    不为满足示例擅自引入 Abseil、内部包、测试框架、构建系统或新的依赖。
    不自动升级 C++ 标准、Go 工具链、Python 最低版本或格式化器。

## 按任务读取规则

只加载当前任务相关的参考文件；多语言改动分别加载，并采用同一套报告方式。

| 目标 | 必读内容 | 重点检索词 |
| --- | --- | --- |
| C++：`.cc`、`.cpp`、`.h`、`.hpp` | [C++ 规范](references/cpp.md) | `CPP-`、头文件、所有权、生命周期、异常、命名 |
| Go：`.go` | [Go 规范](references/go.md) | `GO-`、context、错误、接口、goroutine、测试 |
| Python：`.py`、`.pyi` | [Python 规范](references/python.md) | `PY-`、导入、注解、资源、docstring、日志 |
| Markdown：`.md`、README、设计与 API 文档 | [Markdown 规范](references/markdown.md) | `DOC-`、标题、链接、代码块、目录、平台 |
| 要选择检查工具或输出审查结论 | [验证与审查流程](references/verification.md) | 工具、检查范围、状态、发现格式 |
| 要查原文、判断规则强度或更新摘要 | [来源与适用边界](references/sources.md) | 官方入口、版本、许可证、更新 |

不要仅凭文件扩展名改变项目惯例，例如把现有 `.cpp` 批量改为 `.cc`。
语言细节以对应参考文件及原文为准；本入口不复制全部条款。

## 保留规则强度

在阅读规则和报告发现时保留以下区别。强度与问题严重程度分开判断。

| 标签 | 执行方式 |
| --- | --- |
| 必须 | 在该规则适用的 Google 风格范围内执行明确要求或禁令，先检查所列例外。 |
| 默认 | 正常情况下采用；遇到原文允许的例外、项目约定或兼容性约束时说明取舍。 |
| 建议 | 按可读性、成本和上下文评估，不据此单独阻断合并。 |
| 允许／例外 | 仅表示可使用或可豁免，不转化为全局强制要求。 |
| 工程实践 | 为应用规范补充的流程或验证建议；不能声称是 Google 原文硬性规定。 |

Go 的核心 Guide 优先于 Decisions；Best Practices 是辅助建议。
来源文件的地位不能代替句子本身的强度，例如 Decisions 中的“建议”仍是建议。
一条内容包含多个标签时，分别判断各句要求，不将建议部分升级为强制。
`CPP-*`、`GO-*`、`PY-*`、`DOC-*` 是本技能的追踪编号，不是 Google 官方章节号。

## 实施流程

1.  **建立约束。** 用简短文字记录目标、受影响文件、工具链版本和明确的项目例外。
    对无关语言不要输出一整套检查清单。
2.  **先查语义。** 检查接口契约、错误路径、生命周期、共享可变状态与并发退出条件。
    接着检查命名、组织、注释与格式；不要用格式化结果替代语义审查。
3.  **匹配条款。** 从参考文件定位规则编号与来源，确认适用条件和允许的例外。
    不凭旧版记忆覆盖本技能记录的现行条款。
4.  **做最小修改。** 让改动直接服务用户目标，保留现有行为、公开接口与数据格式。
    避免顺手重命名公共符号、重排整仓库或引入无关抽象。
5.  **同步文档。** 修改接口、错误语义或资源使用约定时更新相应注释和文档。
    代码中的注释与文档语言遵循仓库约定；对用户的说明默认使用中文。
6.  **按风险验证。** 执行项目已配置且与本次改动相关的检查。
    纯格式或文档小改动验证格式、链接或渲染即可；行为改变时验证相关行为。
    记录实际执行的命令与结果，缺少工具时明确标为未执行。
7.  **复查差异。** 确认没有无关文件、未说明的依赖变化、误删注释或不必要的格式波动。
8.  **交付结果。** 先给结论，再给重要发现、修改说明、验证结果及尚存限制。
    用户只需要代码时遵守其格式要求；不要强行输出长篇规范讲解。

## 审查输出

仅输出有具体证据的问题，优先级按实际影响确定。
将潜在错误、规范偏差和可选改善明确分开；低风险样式偏差不标成高危缺陷。
每条发现至少包含：

-   位置：文件与可定位的代码位置。
-   规则：`CPP-*`、`GO-*`、`PY-*` 或 `DOC-*`，以及规则强度。
-   现象与影响：具体代码怎样违反适用规则，会产生什么后果。
-   最小修正：给出能落地的建议或必要片段。
-   依据与例外：引用对应官方章节；说明已经核对的项目约定或适用例外。

没有发现时说明已审查的范围和未验证事项，不宣称整个项目完全合规。
完整报告结构与工具选择见 [验证与审查流程](references/verification.md)。

## 防止常见误用

-   不给 Go 加 80／100／120 列硬上限；不把其他语言的命名规则套给 Go 常量。
-   不把 Python 的 80 列默认值和某个格式化器的默认值混为一谈。
    不把公开 API 的注解要求扩展成“全部函数必须注解”。
-   不依据旧版 C++ 摘要认定“所有输出参数必须为指针”或“RTTI 一律禁止”。
    对标准版本、modules、coroutines 等限制读取 C++ 专项条款。
-   不将 `[TOC]`、站点根路径或 Gitiles 行为视为所有 Markdown 平台的通用能力。
-   不把参考文件中的示例命令当成已执行结果，也不把推荐检查器说成唯一官方选择。

## 原文核验与更新

离线使用时明确这是上述日期的摘要。用户要求最新规则、遇到版本敏感语法，
或条款与项目实践存在实质冲突时，打开对应官方章节核验。
核验失败就保留已确认的范围和不确定项，不编造最新结论。
更新时同时检查规则强度、例外、来源锚点与示例，保留已有规则编号的可追溯性。
